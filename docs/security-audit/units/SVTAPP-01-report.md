### SVTAPP-01-F01: 404 page picks the brand from an exact host list, so some SVT hosts get the WHT 404
- Severity: MEDIUM
- Confidence: high (code), medium (reachability on the platform)
- Status: CONFIRMED_BY_STATIC_EVIDENCE (the mismatch); REQUIRES_RUNTIME_VALIDATION (what the platform forwards as Host)
- CWE: CWE-290 / CWE-697 (inconsistent comparison)
- Files and lines: src/app/global-not-found.tsx:17-22; compare config/brand-routing.js:27, 33, 61-62 and src/lib/brand.ts:65-72
- Evidence: the 404 page lower-cases the Host header, drops the port and tests `routing.SVT_HOSTS.includes(host)`. The router's own rule (`svtHostPattern`) also treats every subdomain of the SVT registrable domain and the trailing-dot spelling as SVT, and `brandFromHost` in src/lib/brand.ts does the same. The 404 page does neither. On a host such as `<anything>.studentvisatax.com.au` or `studentvisatax.com.au.` the rewrite sends an unknown path into `/svt-site/...`, nothing matches, and the global 404 renders the `else` branch: WHT colours and the WHT WhatsApp link built by `waUrl({ topic: 'general', lang: 'en' })` with no "Student Visa Tax" prefix.
- Root cause: a third, weaker copy of the host-to-brand rule. Round 2 fixed the router and `brandFromHost`, and this file was left on the plain list.
- Attack prerequisites: a request that reaches the deployment with a Host the router classes as SVT but the list does not name (trailing dot, or any subdomain that DNS and the platform route to this project). No login.
- Impact: cross-brand leak on the student domain (WHT look and WHT chat entry point; the student arrives in the shared inbox without the SVT marker, so staff and the bot may treat the chat as WHT). No data exposure.
- Recommended fix: decide the brand with `brandFromHost()` (or export one matcher from config/brand-routing.js and use it in all three places).
- Regression test: unit test rendering `GlobalNotFound` with Host `studentvisatax.com.au.`, `app.studentvisatax.com.au` and `STUDENTVISATAX.COM.AU:443`; expect the SVT WhatsApp text and SVT colours in each.
- Limits of this verification: not run. I did not verify whether Vercel normalises a trailing-dot Host before the function sees it, or whether any subdomain is attached to the project.

### SVTAPP-01-F02: The private SVT form path is shipped in every public SVT page
- Severity: MEDIUM
- Confidence: medium
- Status: STRONGLY_SUSPECTED
- CWE: CWE-200 / CWE-540
- Files and lines: src/components/svt/SvtDocument.tsx:9, 27 (rendered by src/app/(svt)/layout.tsx:36, src/app/(svt-vi)/layout.tsx:23, src/app/(svt-zh)/layout.tsx:23); src/components/layout/Analytics.tsx:1, 52-68; form pages src/app/(svt)/svt-site/jhd7hp9xd/page.tsx:8-17 and the /zh and /vi copies
- Evidence: the form pages say the form is "reached from the link we send on WhatsApp, never from search", and config/form-paths.js exists to keep the slugs random and resettable. But `SvtDocument` passes the three form paths as the `untagged` prop to `Analytics`, which is a `'use client'` component. Props of a client component are serialised into the page payload, so the form slug is present in the HTML of every public SVT page in all three languages. The second-step slug is also in the client bundle of the form (form-brand-svt.tsx:145-147).
- Root cause: a secret-by-obscurity path used as configuration data for a client component in the shared shell.
- Attack prerequisites: none; view source of any SVT page.
- Impact: anyone can open the tax form without first agreeing a price on WhatsApp once `SVT_FORMS_ENABLED=true`, and can post to the two allowed API routes from the SVT host. Whatever protection the form path was meant to add is gone; the API routes must stand on their own (rate limit, body limit, upload checks: other units). While the flag is off the page shows the closed notice, so today the impact is disclosure only.
- Recommended fix: do not send the path to the client. Either decide "untagged" on the server (render `Analytics` with a boolean from the form route's own layout or page), or mark the form pages with a data attribute that `Analytics` reads. Do not rely on the slug as an access control in any case.
- Regression test: build-output test that greps the static HTML and RSC payload of `/`, `/zh`, `/vi` and one guide for both SVT slugs from config/form-paths.js and expects no match.
- Limits of this verification: no build was run, so I did not see the payload; this rests on standard Next.js behaviour for client-component props.

### SVTAPP-01-F03: Refund guarantee is published for every return, not only TFN-only returns
- Severity: MEDIUM
- Confidence: medium
- Status: CONFIRMED_BY_STATIC_EVIDENCE (the text); business rule taken from the audit brief
- CWE: n/a (business logic / misleading representation)
- Files and lines: src/lib/svt/llms.ts:34-37; source text src/lib/svt/content/home-en.ts:43-53; same wording src/lib/svt/content/guides-en.ts:65, 84-88
- Evidence: llms.txt prints "Price: $220 ... $385 with ABN work" and on the next lines "Guarantee: if your refund is smaller than our fee, we pay you the difference" plus the terms. The only exclusions stated are "no refund, or you owe tax". Nothing limits the guarantee to the $220 TFN-only return; the pricing page's meta description puts the $385 ABN price and the guarantee in one sentence.
- Root cause: the guarantee copy has no scope clause, and llms.ts repeats it to answer engines as a fact about the service.
- Attack prerequisites: none. An ABN customer ($385) with a small positive refund can claim the difference.
- Impact: financial exposure and a public promise the business does not intend to keep for ABN returns; answer engines will repeat it.
- Recommended fix: add the scope to the guarantee terms in the content source (all three languages) and in llms.ts, e.g. "for returns with TFN income only".
- Regression test: content test asserting that every string containing the guarantee sentence, and the llms.txt output, also contains the TFN-only scope wording in each language.
- Limits of this verification: I read the English home and pricing guarantee blocks only, not the zh/vi texts or the Client Agreement sections; a scope clause may exist in a place I did not open.
