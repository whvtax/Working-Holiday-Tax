## Findings

### UI-04-F01: Cross-site request guard is declared for /api/mia but never runs, so the Mia dashboard's state-changing calls have no Origin check
- Severity: MEDIUM
- Confidence: high (static), medium (exploitability)
- Status: CONFIRMED_BY_STATIC_EVIDENCE (the gap); REQUIRES_RUNTIME_VALIDATION (the attack)
- CWE: CWE-352
- Files and lines: src/proxy.ts:126 (matcher), src/proxy.ts:61-65, src/lib/request-guard.ts:43; callers in this unit: src/components/mia/MiaStatusBar.tsx:15, src/components/mia/MiaPipeline.tsx:30; routes: src/app/api/mia/status/route.ts:13-16, src/app/api/mia/move/route.ts:9-16, src/app/api/mia/send/route.ts:9-17
- Evidence: `GUARDED_API_PREFIXES` lists `/api/mia/`, and the proxy applies `crossSiteMutationReason` to guarded paths, but the proxy `config.matcher` lists only `/crm`, `/atlas`, `/api/crm/:path*`, `/api/will/:path*` and `/api/atlas/:path*`. The proxy is therefore not invoked for `/api/mia/*`, and no Mia route calls the guard itself (the only per-route use is `/api/will/actions`). The Mia routes authenticate with the `crm_session` cookie only and parse the body with `req.json()` without checking the content type, so a plain HTML form (`enctype="text/plain"`) can deliver a valid JSON body with no preflight. The 17 Nov test file exercises `isGuardedApiPath` only, not the matcher, so it passes while the guard is inactive.
- Root cause: the prefix list and the proxy matcher are two separate lists; `/api/mia/` was added to one and not the other.
- Attack prerequisites: a logged-in CRM operator visits attacker-controlled content on a host that is same-site with the CRM host (any sibling subdomain of the registrable domain, the case the guard's own header comment names). `SameSite=Strict` on `crm_session` (login/route.ts:105, verify-otp/route.ts:93) still blocks fully cross-site pages.
- Impact: forged pause or resume of Mia (`/api/mia/status`), forged pipeline moves of any SVT customer to any state (`/api/mia/move`), forged draft messages saved against a customer (`/api/mia/send`, drafts only, nothing is sent). `/api/mia/form-link` is also unguarded, but its signed link is returned in the response body, which a forged cross-origin request cannot read.
- Recommended fix: add `'/api/mia/:path*'` to the matcher in src/proxy.ts; better, derive the API part of the matcher from `GUARDED_API_PREFIXES` so the two cannot drift. Also reject non-`application/json` bodies on these routes.
- Regression test: import `config.matcher` from src/proxy.ts and assert every entry of `GUARDED_API_PREFIXES` has a matching matcher entry; plus a request-level test that `POST /api/mia/status` with `Sec-Fetch-Site: same-site` returns 403 `bad_origin`.
- Limits of this verification: nothing was run. I assumed the standard Next behaviour that the proxy runs only for matcher paths. I did not check which sibling subdomains exist or are attacker-reachable. src/app/api/mia/clients, pipeline and tasks routes were not opened.

### UI-04-F02: Mia expense form turns thousands-separated amounts into the wrong figure
- Severity: MEDIUM
- Confidence: high
- Status: CONFIRMED_BY_STATIC_EVIDENCE
- CWE: CWE-20
- Files and lines: src/components/mia/MiaExpensePdf.tsx:16-17
- Evidence: `Number(amount.replace(',', '.'))` replaces the first comma with a decimal point. Typing `1,250` gives 1.25 and passes the `Number.isFinite` and `>= 0` checks, so it is posted and written into the PDF. `1,250.00` becomes NaN and is rejected, so the behaviour is inconsistent as well as wrong. The result line shows only the saved path, not the amount, so the operator gets no chance to notice.
- Root cause: one replace call serves both a decimal comma and a thousands separator.
- Attack prerequisites: none; ordinary staff input.
- Impact: an income or expense figure 1,000 times too small in a customer's tax working document, with no warning.
- Recommended fix: accept one explicit format. Reject any input with both separators or with a comma followed by exactly three digits, or strip thousands separators deliberately, and echo the parsed amount in the result message.
- Regression test: unit test of the parser: `1,250` and `1,250.00` must be rejected or parsed as 1250, `12,50` as 12.5 only if decimal commas are intended, `12.50` as 12.5.
- Limits of this verification: I did not read `parseItems` in src/lib/will/expense-pdf.ts in full, so a server-side sanity check may exist; none can know the intended figure.

### UI-04-F03: Each "Build PDF" from Mia silently replaces the customer's existing PDF for that category
- Severity: LOW
- Confidence: medium
- Status: CONFIRMED_BY_STATIC_EVIDENCE (overwrite); impact depends on workflow
- CWE: CWE-362 / n/a (lost update)
- Files and lines: src/components/mia/MiaExpensePdf.tsx:22-25; src/app/api/crm/expense-pdf/route.ts:38-46 (`upsert: true`); src/lib/will/expense-pdf.ts:59 (path = prefix/customerId/taxYear/category slug)
- Evidence: the form can send exactly one item per request, with category defaulting to `Income`. The storage path depends only on customer id, tax year and category, and the upload uses `upsert: true`. A second item for the same category therefore replaces the first PDF, and also replaces any multi-item PDF built elsewhere for that customer, year and category. The route does not check that `customerId` exists or belongs to SVT; it accepts any id matching the pattern.
- Root cause: single-row UI on top of a whole-document, overwrite-on-save endpoint.
- Attack prerequisites: valid CRM session (staff).
- Impact: loss of a previously built working document without warning; PDFs can be stored under an id that is not a customer.
- Recommended fix: let the form hold several rows before building, or have the endpoint refuse to overwrite without an explicit `replace` flag; verify the customer exists before saving.
- Regression test: build twice for the same customer, year and category and assert the second call either fails without `replace` or the PDF contains both items.
- Limits of this verification: I did not read the Will-side expense UI or `/api/crm/expense-pdf/from-task`, so I do not know whether overwrite is the accepted behaviour there.

### UI-04-F04: Mia pause toggle has no error handling, so a failed pause can look like a successful one
- Severity: LOW
- Confidence: high
- Status: CONFIRMED_BY_STATIC_EVIDENCE
- CWE: CWE-755
- Files and lines: src/components/mia/MiaStatusBar.tsx:13-18
- Evidence: `toggle` awaits `fetch` and `r.json()` with no try/catch. A network failure or a non-JSON response (for example an HTML error page) throws an unhandled rejection; no error is shown and the label stays as it was. The sibling components (MiaPipeline.tsx:27-37, MiaExpensePdf.tsx:18-31) do handle this.
- Root cause: missing error path.
- Attack prerequisites: none; any transient failure.
- Impact: the operator clicks "Pause Mia", sees no error, and may assume the agent is paused while it keeps running (or the reverse).
- Recommended fix: wrap in try/catch, show an alert-role message, and re-read `/api/mia/status` after every toggle.
- Regression test: component test with `fetch` rejecting, and with a 500 HTML body; assert an error is rendered and the label is unchanged.
- Limits of this verification: static only.

### UI-04-F05: "Random" form slugs, including the other brand's, are shipped in public client code
- Severity: INFORMATIONAL
- Confidence: medium
- Status: REQUIRES_RUNTIME_VALIDATION
- CWE: CWE-200
- Files and lines: src/components/layout/PublicShellClient.tsx:31-37; src/components/ui/form-brand-wht.tsx:4,17-20; src/components/svt/SvtDocument.tsx:9,27; config/form-paths.js:16-27
- Evidence: PublicShellClient is a client component in the shell of every public WHT page and hardcodes all WHT form slugs. form-brand-wht.tsx is a client module that imports the whole of config/form-paths (a CommonJS object holding the WHT, SVT and retired slugs), so the SVT form slugs probably ship in the WHT bundle. SvtDocument passes the SVT form paths as a prop to the client `Analytics` component, so they appear in the page payload of every SVT page.
- Root cause: slug lists needed for layout and analytics decisions live in client code.
- Attack prerequisites: none; read the site's JavaScript.
- Impact: the slugs give no secrecy. That is acceptable only because form access rests on the signed `?k=` token, not on the slug. The cross-brand point contradicts the stated rule in src/lib/svt/brand-public.ts:4-8 that one brand's pages must not carry the other's identifiers.
- Recommended fix: treat slugs as public in all documentation and gating decisions; import only `formPaths.WHT` through a WHT-only module in the WHT client bundle.
- Regression test: extend the existing "scripts loaded by each brand" e2e check to assert the SVT slugs are absent from WHT chunks.
- Limits of this verification: no build was run, so bundle contents are inferred from imports. I did not verify that the form submission routes enforce the token.
