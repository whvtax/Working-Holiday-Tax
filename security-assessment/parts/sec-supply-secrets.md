Date: 2 Nov 2026. Method: static review plus local harmless checks. No production access, no values printed (all matches below are file:line and type only).

## Scope covered

- .gitignore, vercel.json, next.config.js (build settings only), scripts/, e2e/, test-results/, marketing/, docs/, .data/, .audit-state/, .claude/ (vendored tooling), .mcp.json. No .github/, no Dockerfile, no .vercelignore, no .npmrc, no .git directory exists in this copy.
- Semgrep 1.182.1 was available locally. No local rule packs are installed, and registry packs (p/...) need a network fetch, so I used 14 hand-written local rules (`scratchpad/semgrep/local.yml`, metrics off, no upload) over src, scripts, e2e, next.config.js (654 files). 371 raw hits, nearly all false positives (see Semgrep triage).

## Verdict in one line
No committed secrets found. Production dependencies have zero known vulnerabilities. The real exposure is process: the project is shipped as a zip (PROJECT_HANDOFF.md:267), so `.gitignore` does not protect it, and there is no CI.

### Semgrep triage (local rules only)
371 raw hits, 0 real vulnerabilities.
- `dangerouslySetInnerHTML` (309): all are `application/ld+json` with `JSON.stringify` of first-party data or static CSS strings (RootDocument.tsx:312 additionally escapes `<`, `>`, `&`, U+2028/9; svt/jsonld.ts `jsonLd()` helper). No user-controlled input reaches them. Informational: some other JSON-LD sites use plain `JSON.stringify` without the `<` escape; safe today because the data is static and first-party; adopting one shared escaping helper would be a cheap defence-in-depth change (not applied, touches many files and SEO output).
- `child-process` rule (22): all `RegExp.exec()` false positives.
- `non-timing-safe-compare` (14): array/length checks and variable names containing "token/signature", not secret comparisons. src/app/api/crm/login/route.ts:32 is a type/length check. Real secret comparison paths belong to the auth and webhook agents.
- `console-log-sensitive` (5): log fixed strings plus the caught error object (login/route.ts:83,140; verify-otp/route.ts:92; tfn-form/route.ts:67,111). No field values logged. Informational: `console.error('...', err)` on the TFN form routes logs the raw error object, which could in theory echo request data from a library error; a redaction wrapper would be defence in depth (logging agent).
- `redirect` (7): all in /crm pages redirecting to fixed paths.
- `string-sql` (1): store-supabase.ts:1284 is a query-builder `.select('*')`, not string SQL.
- No `eval`, `new Function`, `innerHTML =`, `document.write`, disabled TLS, or MD5/SHA1 usage in src.
- Math.random (8): not reviewed as a vulnerability here; check none generate tokens/OTPs (auth agent covers OTP; the file link slugs use `crypto.randomBytes` in scripts/reset-form-links.mjs:21).

### P4. CI workflow (SC-13), free, no external services, no code upload
```diff
--- /dev/null
+++ b/.github/workflows/ci.yml
@@
+name: ci
+on:
+  pull_request:
+  push: { branches: [main] }
+permissions: { contents: read }
+jobs:
+  verify:
+    runs-on: ubuntu-latest
+    steps:
+      - uses: actions/checkout@v4      # pin to a commit SHA when adding
+      - uses: actions/setup-node@v4    # pin to a commit SHA when adding
+        with: { node-version: 22, cache: npm }
+      - run: npm ci --ignore-scripts
+      - run: npx tsc --noEmit
+      - run: npm run lint
+      - run: npx jest --forceExit
+      - run: npm audit --omit=dev --audit-level=high
+      - run: npx semgrep --metrics=off --config .semgrep/local.yml src   # optional, local rules only
```
`npm ci --ignore-scripts` is safe for lint/tsc/jest here because the only install-script packages are fsevents and unrs-resolver; if eslint's import resolver complains, drop the flag for that step. Pair with branch protection (require the `verify` check, no force pushes) once a repo exists. Secret scanning: GitHub's free secret scanning/push protection on private repos depends on the plan; the jest secret scan above covers the gap at no cost. Optional: pre-commit `gitleaks protect --staged` run locally (open source, no upload).

## Devil's Advocate
- "Is SC-02 real?" It depends on how the zip is made. If Jo zips from a clean export and `.data/` only exists locally, nothing leaks. But the handoff says "before a zip" and `.data/store.json` is sitting in this very copy, so the failure mode is one careless `zip -r .` away. Rated Medium because of the data kinds involved (it records real customers and the WhatsApp token when Supabase env is absent, per .gitignore:9-12), not because a leak has been shown. Today's file is synthetic, which lowers actual harm to nil.
- "Could the `.gitignore` change break anything?" `.env.*` also ignores `.env.example` unless the negation applies; the `!.env.example` line is placed after it and ordering is correct. Nothing in the repo is committed under another `.env.*` name (find showed only `.env.example`). Zero build impact.
- "Could the jest guardrails block a legitimate change?" Yes, deliberately: adding a production dependency, a new install-script package, or a string that looks like a key fails the suite. The failure message names the file and rule. Risk of false positives is low (tested clean on the whole tree); the credentialed-URL rule could trip on a doc example like `redis://user:pass@host`, in which case use a placeholder with no colon-password pair.
- "Is the dev audit being too lenient?" Moderate dev-tool ReDoS (minimatch, glob) matter only if untrusted globs are fed to lint/test tooling; they are not. Applying npm's suggested fix would downgrade eslint/jest by majors and break the toolchain, so ignoring is right.
- "Is the HEIC finding overstated?" Possibly; I rated it Low/Suspected because I did not run a bomb file (no uploads of crafted files in scope). Fix, if wanted, is to reject HEIC over a byte threshold or run with a timeout; Category B (uploads), so left as a recommendation.
- "Would CI or Dependabot cause noise or downtime?" Dependabot PRs can be ignored without effect; grouped dev updates and a 3-PR cap keep it quiet; major bumps for next/react are ignored by config. CI does not touch production and does not deploy.
